## 修复：相对 .md 链接点击后仍为空白（路径百分号编码导致 set_file 找不到文件）
- 现象：GUI 中点击指向其他 .md 的相对链接（尤其含中文/空格文件名，如 `09-Kotlin 重构决策与风险.md`），不渲染目标文件、显示空白。
- 根因：`frontend/src/App.vue` 的 `resolveAndOpen` 用 `new URL(href, base).pathname` 解析相对链接。WHATWG URL 会把中文等非 ASCII 字符百分号编码（`我的笔记`→`%E6%88%91...`、中文文件名→`%XX`），而 `%20` 又被解码成空格，得到「半编码」混合路径，与磁盘真实路径不符。Rust `set_file` 用 `PathBuf::from` 直接拼、不解码百分号 → 判定文件不存在 → 导航失败（空白）。
- 修复：改为 `decodeURIComponent(new URL(href, base).pathname)`，把 pathname 还原成真实文件路径；`resolveAndOpen` 改为 async，当 `currentPath` 为空时回退调用 `get_file_path`（Rust 端权威路径）；目录截取正则改为分隔符无关 `[\\/][^\\/]*$`。最终仍调 `openMdFile` 以 HTML 重新渲染目标 .md。
- 验证：Node 模拟——修正前 target 为 `%E6%88%91...` 半编码路径；修正后正确还原为 `/Users/edy/docs/我的笔记/09-Kotlin 重构决策与风险.md` 等（`./`、`../` 也正确）。`pnpm build` 通过，产物含 `decodeURIComponent`。
- 注：Windows 路径（`C:\...`）下 `file://` base 拼接仍不理想，用户当前为 macOS，未深究。

## 修复：全宽"没有作用" + 收起目录树后 260px 空间仍占位
- 现象：全宽开启后正文仍被左侧目录树挤占一大块；有时手动收起目录树，但空间没释放。
- 根因 1（全宽无效）：`.sidebar` 是 `position:fixed`，正文 `.main-content` 始终 `margin-left:260px` 给侧栏留位。首版全宽只放开 `--layout-max-width` 并把 `--content-max-width` 设 98%，但 98% 是相对"已被侧栏吃掉 260px 的剩余宽"算的，侧栏那 260px 从未让出 → 全宽形同虚设。
- 根因 2（收起后空间不变）：`templates/mpe.html` 旧规则 `.sidebar.collapsed + .main-content{margin-left:0}` 选择器失效——`.sidebar` 的相邻兄弟是 `.sidebar-resizer` 而非 `.main-content`，永远匹配不到。点击按钮时 JS 内联置 0 才生效；一旦刷新从 localStorage 恢复 collapsed，JS 不再置 0，260px 就一直留着。
- 修复：
  - `template.rs` 全宽注入改为：`:root{--layout-max-width:none!important;--content-max-width:98vw!important}` **且** `.sidebar,.sidebar-resizer,.sidebar-toggle{display:none!important}` + `.main-content{margin-left:0!important;padding-left/right:1vw!important}`，正文真正占满约 98vw。
  - `mpe.html` 把失效的相邻兄弟选择器改为 `body.sidebar-collapsed .main-content{margin-left:0!important}`（body 在收起时加 `sidebar-collapsed` 类），刷新后也能正确释放 260px。
- 验证：全宽 HTML 注入确认含三条规则；默认 HTML 侧栏不被隐藏（6 处 display:none 均为 print/响应式断点）；新收起规则存在、旧失效选择器为 0。
- 二次修复（仍见两边大空白）：把全宽改成真正 100% 撑满——`.markdown-body{max-width:100%!important}` + `.layout{max-width:none}` + `.main-content{margin-left:0;padding:24px}`，不再用 `vw`（避免 iframe 视口差异导致 `98vw` 失效）。
- ⚠️ 关键坑：全宽 CSS 在 `template.rs` 用 `include_str!` 嵌入、编译进 **Rust 二进制**。GUI 里只 `pnpm build` 前端**不会**更新全宽效果，必须重编 Rust：`cargo run -p md2x-gui`（或 `cargo build -p md2x-gui`）。排障时先用 CLI 生成 HTML 在浏览器打开验证（绕过 GUI 重建歧义）。
- **用户误判澄清**：用户怀疑 `@media (max-width:900px)` 设了固定宽度导致留白——实测该媒体查询只 `display:none` 侧栏、`margin-left:0`、`padding:24px 20px`，**没碰 max-width**，不是元凶。真·固定宽度来自默认 `.layout{max-width:1200px}` + `.markdown-body{max-width:860px}`，全宽时已被 `!important` 覆盖成 `none`/`100%`。
- **Chrome 无头实测隔离验证法（很有效）**：用 `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu --no-sandbox --dump-dom --virtual-time-budget=3000 --window-size=W,H "file://...html"`，并在 HTML 末尾注入一段 `window.load + setTimeout` 把各层 `getBoundingClientRect().width`/`getComputedStyle().maxWidth/marginLeft` 写进 `<pre id=MEASURE>`，从 dump-dom 输出里 `grep -o 'MEASURE={[^<]*'` 读取——能精确量化"视口 vs 各层真实宽度"，直接证明 CSS 是否真满宽，绕开 GUI 进程歧义。实测：全宽版 viewport=1400 时 markdownBody=1352（仅24px边距，满宽）；默认版 markdownBody=828（左右大留白，符合 860px 写死）。
- ⚠️ **真·根因（推翻"旧进程"结论）**：GUI 全宽按钮"点了没反应"不是旧进程，而是 **Tauri v2 命令参数大小写 bug**。Tauri v2 的 `#[tauri::command]` 参数默认 `rename_all = "Keep"`（见 `tauri-macros-2.6.3/src/command/wrapper.rs:52`），**不会**自动把 JS camelCase `fullWidth` 转成 Rust snake_case `full_width`。JS 传 `fullWidth` 时 Rust 端是未知字段 → serde `deny_unknown_fields` reject → `invoke` 抛错被前端 `catch` 吞掉 → 页面完全不更新（表现为"按钮没反应"）。**修法**：后端命令参数名直接改成 camelCase `fullWidth`（与 JS 完全一致），不依赖任何大小写转换。这是反复失效的真凶，旧进程只是次要干扰。
- 教训：前端 `invoke` 的 `catch` 会静默吞掉参数为空 reject 错误，导致"按钮无效果"极难排查。以后新增/改 Tauri 命令参数，要么 JS 与 Rust 用**完全相同**的命名，要么显式 `#[tauri::command(rename_all = "snake_case")]` + JS 传 snake_case。
